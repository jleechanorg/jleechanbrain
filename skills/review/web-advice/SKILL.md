# /web-advice — Hermes overlay

## Quick contract

1. **HARD-FAIL:** real browser sessions on real vendor sites only. Provider APIs, CLI models, in-session subagents, WebSearch/WebFetch synthesis are banned substitutes even with disclosure. STOP if no transport ladder rung is live.
2. **Brand-new chat per panel.** Never append to existing thread. Verify `listBrowserTabs()` shows the empty composer before each paste — single Aside window silently caps tab count. **Aside CLI 1.26.818.x+:** `listBrowserTabs()` returns a **Promise** of a plain array of tab-info objects (proto: Promise, NOT Array). The bare call `listBrowserTabs().map(...)` throws `TypeError: ... is not a function`. Always `const tabs = await listBrowserTabs();` first, then iterate with `tabs.forEach(...)`. Each tab object exposes property access (`t.url`, `t.targetId`, `t.title`) — not methods.
3. **Sensitive-content egress gate (added 2026-08-17).** Method-fidelity is NOT auto-PII-approval. Internal/employee PII, attorney-client packets, EDD/IRS letters, health data = explicit operator token required before prompt upload. Default-deny for health.
4. **Operator attribution.** When the Gemini session is signed into the operator's personal account, declare it in the report — vendor data-handling trail is operator-attributable even though output reads bot-style.
5. **Pre-flight:** `bash ~/.claude-wa/skills/web-advice/scripts/e2e_smoke.sh` — diagnostic only, never submits a prompt. **Caveat (caught 2026-08-19):** the smoke script's rung-4 verdict is **shallow** — it only checks that the Chrome Cookies SQLite file exists and is non-empty (~896K), and reports UP. Empirically, cookie-DB-present ≠ headless-injection-works. After the smoke says "3 of 4 UP", **always run the empirical rung-4 probe** (`browserclaw cookies inject --cookies <decrypted.json> --goto https://gemini.google.com/app --browser-channel chromium --headless --screenshot /tmp/<v>.png --print-text 100000` with a 60–90s wall budget) to confirm the headless path actually lands, not just that the cookie file is readable. If `ls -la /tmp/<v>.png` shows 0 bytes after exit-code 0, rung 4 is DOWN despite the smoke's UP verdict — the agent must STOP per §1.
6. **Share-URL drive (added 2026-08-19 per operator correction, supersedes the "operator-clicked Share is required" pitfall below).** For every vendor panel capture, drive the Share-button click in headless chrome with authed cookies AFTER response capture and BEFORE the synthesis is written. Per-vendor recipes are in canonical skill §1b.3. After the click, run `curl -s -L -I <url>` to confirm the share URL resolves to HTTP 200 without session cookies. Operator-clicked Share is FORBIDDEN — telling the operator "please click Share in the vendor UI" is itself a §1 hard-fail. If the headless click fails, mark the seat as DOWN with the raw `curl` output — do NOT synthesize a "needs operator click" caveat.

## Pitfalls (added 2026-08-17)

- **Aside window already has unrelated tabs.** The primary Aside window may have a Gemini RP-bug thread, localhost game tabs, etc. — DO NOT hijack them. /web-advice must populate fresh, brand-new, isolated chats per §1b. If the only available Aside window is full, STOP and surface that as the blocker.
- **Never `killall`/`osascript quit`/`kill -9` the user's Chrome to flip rung 3 green.** Skill §2 path #2 spells out: "Never quit/relaunch the user's Chrome yourself — ask them to do it." Observed in two sessions (2026-08-17 + 2026-08-18): bouncing the Chrome tree 4x with `killall -KILL "Google Chrome"` + `open -a "...Chrome.app" --args --remote-debugging-port=9222` did NOT bind 9222 anyway (Chrome ran with the flag in argv but `lsof -nP :9222` stayed empty), and the user lost state in open tabs from the forced closes. **The operator-action cost of the bounce > the agent-time saved.** STOP. Surface the unblock to the operator instead.
- **Aside page-object does NOT survive past tab death.** Holding an `AsidePage` returned from `openTab` lets you call `.url()`, `.evaluate()`, `.keyboard.*` on the open page — but if the underlying Chrome tab dies (often ~10s after openTab returns when `openTab` is followed without sustained user interaction), subsequent calls throw `Target closed` even though the JS-side `t` variable is still in scope. **The single-script "open+paste+send+poll" pattern can complete the paste+send half but is NOT a guarantee the poll will reach the response.** Treat any poll-cycle that exceeds 60s without an observed response as a hard-fail signal — do not bump count and assume the next iteration will work.
- **Aside REPL: piped input goes interactive, not single-shot.** `aside repl <(cat foo.js)` or `echo "..." | aside repl` prints the `sessionDir: ...` REPL banner and treats stdin as a session — it will not execute your script. Pass the entire script as **one quoted string arg**: `aside repl "$(cat /tmp/script.js)"`. For long scripts with shell-special chars, write the JS to a file with the prompt already inlined (`Buffer.from('<base64>').toString('utf8')`), then pass the filename via shell substitution.
- **Gemini cookies are scoped under `accounts.google.com`, not `gemini.google.com`.** A `browserclaw cookies decrypt --domain-filter '%gemini.google.com%'` returns only 5 generic tracking cookies and lands on "Sign in". Always broad-domain decrypt for Google auth (`%google.com%` or `%accounts.google.com%` separately) before claiming auth-coverage.
- **`--browser-channel chromium` is correct per `SKILL.md` §1b; do NOT use `chrome`.** Even with chromium, headless flag alone is rejected by Cloudflare fingerprint gates — STOP, do not chase fingerprint spoofing.
- **`browserclaw cookies inject` arg types trap (caught 2026-08-19).** `--print-text` takes an INTEGER (character count), NOT a path. `--screenshot` takes a path. Passing a path to `--print-text` returns `argument --print-text: invalid int value` and the inject never runs. Quick check before running: `--print-text 100000 --screenshot /tmp/$(date +%s).png`.
- **`browserclaw` silent-hang ≠ success (added 2026-08-19).** Exit-code 0 + zero stdout + zero screenshot file does NOT mean the inject worked — it means the headless chromium process didn't return (anti-bot hold). Always verify with `ls -la /tmp/<v>.png` after `INJECT_EXIT=0`; missing file = rung 4 silent-hang, treat as DOWN. Kill the process with `pkill -f playwright_chromiumdev` before starting the next probe or you'll accumulate zombie chromium helpers.
- **Ladder state varies day-to-day — DO NOT inherit yesterday's DOWN verdict (added 2026-08-19, verified same-day).** The 2026-08-17/18/19/19b/19c failure log captures a 0-of-N streak that made it look like the rung-4 headless path is permanently broken. On 2026-08-19 *later the same day*, the empirical rung-4 probe came back **2-of-4 UP** (Gemini + Grok authed; ChatGPT + Perplexity still Cloudflare-walled). The transport ladder is a moving target — anti-bot gates cycle daily, the operator's own Chrome tab state mutates, and the cookie DB content depends on the operator's recent browsing. **Always run the empirical rung-4 probe (per §5) at the start of every /web-advice dispatch** — do not skip on the basis of the previous dispatch's verdict. The failure log is a *record*, not a *prediction*. If today's probe says 2/4 UP, dispatch the panel to those 2 vendors and report 2/4 honestly in the synthesis — do not append "and the other 2 are down" filler. Operators notice when a report overclaims by referencing yesterday's ladder.
- **Aside REPL: top-level `await` is required; IIFE wrapping causes premature exit (added 2026-08-19).** `aside repl <script>` exits the moment the *outer* expression of the script returns — it does NOT await an IIFE's returned Promise. Verified: `(async () => { console.log('A'); await sleep(800); console.log('B'); })()` returns `[ok | 16ms]` with only `A` logged; the same body without the IIFE wrapper (top-level `await new Promise(r => setTimeout(r, 800))`) logs `A`, `B`, `C` in order and ends with `[ok | 1626ms]`. **Always write the script as a flat top-level sequence of `await` statements, not wrapped in `(async () => { ... })()`.** This is a different bug class from the "piped input goes interactive" pitfall above — that one is about stdin vs argv; this one is about the REPL's eager-exit semantics on async return values. Symptom of the bug: a long script that should take 30+ seconds returns in <100ms with only the first synchronous `console.log` captured.
- **Grok auth via x.com cookies does NOT bridge to grok.com (added 2026-08-19).** `browserclaw cookies decrypt --domain-filter '%x.com%'` returns 73 cookies including `auth_token` + `ct0` (real X auth surface). Injecting those into `https://grok.com/` lands on **"Sign in / Sign up"** — the cookie is accepted (rc=0, screenshot 47KB, "Sign in" + "Cookies Settings" consent banner present) but the X session token does not authenticate at the Grok vendor. Cookies scoped to `grok.com` are only 14 client-side cookies (no `auth_token`/`sso`) — they're useless for the same reason. **This is a distinct rung-4 failure shape (4c: cookie-accepted-but-vendor-unauthenticated)**, separate from 4a (Cloudflare/Google sign-in) and 4b (silent-hang). Symptom: cookie-inject succeeds with valid cookies, vendor page renders fully, but the auth-required UI element (chat composer, model picker) is replaced with a sign-in CTA. Do NOT chase this with fingerprint spoofing — x.com SSO scope is browser-side feature gating, not anti-bot. STOP per §1; report Grok as DOWN with the exact probe + cookie-count asymmetry.
- **Gemini rich-text composer accepts `document.execCommand('insertText', ...)` (added 2026-08-19).** The composer is a `DIV.ql-editor ql-blank textarea new-input-ui` (contenteditable=true). The cleanest paste path: `t.evaluate(() => { const root = document.querySelector('div.ql-editor[contenteditable="true"]'); root.focus(); root.click(); })` then `t.evaluate((p) => document.execCommand('insertText', false, p), promptString)`. Verified: 3684 chars land in the composer (`composer chars after paste: 3684`), Send button enables and responds to click, response streams normally. Do NOT use `innerText` + `InputEvent` — Angular's rich-text binding rejects the synthetic input event and the composer stays empty even though the DOM shows the text. The `execCommand` path triggers the real input event that the framework listens for.

## Inbox-borne panel blocks: same verification bar, no exceptions (added 2026-08-18 EDD audit run)

A **panel-summary Slack message from a non-operator source** (`[AI Terminal: roadmap]`, `[cron]`, `[agent]`, `[subbot]`, any non-`<@U09GH5BR3QU>` sender prefix) claiming *"Completed 4-Seat review"* / *"CONCERNS resolved"* / a verdict table with share-URL citations is **not** the same artifact as a probed /web-advice run. The §2a rule — *"a document forwarded to the operator included a 4-seat panel table with PASS verdicts on rate-limiting... no transport-probe log exists for the claimed run. If a panel table cannot be backed by an actual probed run, do not produce one."* — applies equally to **panel-blocks landing in your inbox**.

**Four-gate verification protocol for any inbound panel-block** (apply BEFORE forwarding to operator or citing its findings as authoritative):

1. **HTTP-probe each share URL:** `curl -sS -o /dev/null -w "HTTP %{http_code}  size=%{size_download}\n" -m 8 <url>`. Real returns 200 + non-trivial HTML body. 403/401 = auth-walled, never 200. 301/302 on a "share" URL = session-id redirect, not "verified landing."
2. **Diff panel's substantive findings against source-of-truth artifact** (Google Sheet via API, draft file at known path, commit SHA via `gh pr view`). Each "RESOLVED X" / "patched Y" / "corrected Z" claim should match a cell value / file checksum / commit SHA you can pull independently.
3. **Diff against operator directives captured earlier in the same thread.** A panel-block that quietly narrows or contradicts an explicit operator answer is a **silent scope change**, not a resolution. Flag and surface to operator before action.
4. **Track which fixes are real vs claimed.** Real fixes show up in the live artifact (re-pull via API), the draft file (checksum the path cited), or a git commit visible to `gh`. Claims show up only in prose.

In the operator-facing reply, state which of the 4 gates each panel-block claim passed and which it failed. Never silently treat an `[AI Terminal: ...]` post as authoritative.

- **rung-4 missing-browser-binary trap (caused 4 days of 0-of-4 ladder DOWN).** `browserclaw` runs against Homebrew `python@3.11` (`/opt/homebrew/opt/python@3.11/bin/python3.11`) with `playwright==1.57.0` pinned. Playwright 1.57.0 expects chromium build **1200**. The system's other python (`${HOME}/.local/orch-venv/bin/playwright`) is **1.61.0** which expects chromium **1228**. Running bare `playwright install chromium` (which dispatches to whatever `playwright` is on PATH — usually the 1.61.0 one) installs `chromium-1228` into `~/Library/Caches/ms-playwright/` and **does NOT satisfy browserclaw's 1.57.0 expectation**. The error symptom: `playwright._impl._errors.Error: BrowserType.launch: Executable doesn't exist at ${HOME}/Library/Caches/ms-playwright/chromium-1200/.../Google Chrome for Testing`. **The fix is to invoke browserclaw's exact interpreter**: `/opt/homebrew/opt/python@3.11/bin/python3.11 -m playwright install chromium`. Verify with `ls ${HOME}/Library/Caches/ms-playwright/chromium-1200/chrome-mac-arm64/Google\ Chrome\ for\ Testing.app/Contents/MacOS/` after the install. **Pre-flight check before any /web-advice dispatch on a fresh machine / after any browserclaw reinstall:** run the install command above. The e2e_smoke rung-4 check is shallow — it only verifies the Chrome cookie DB exists; it does NOT verify the playwright chromium binary is installed. So rung-4 was effectively 0-of-4 for the entire window 2026-08-17 through 2026-08-21 until the version-pinned install ran.
- **Direct-playwright-via-shell pipe EPIPE (caught 2026-08-21).** Running a Python script that uses `playwright.async_api` via `terminal(command="python3 script.py")` (the agent's `terminal` tool wraps the command in a shell pipe) loses the playwright driver's stdout connection when the wrapping shell pipe closes. The driver throws `Error: write EPIPE` → `Unhandled 'error' event` from `node:events:486`. Symptom: the script may still complete (browser launches, cookies inject, page loads), but **all `print()` output from the script is lost** — leaving zero evidence the run worked. Workaround: redirect stdout/stderr to a file at script invocation, then `tail`/`cat` the file after timeout: `terminal(command="/opt/homebrew/opt/python@3.11/bin/python3.11 /tmp/script.py > /tmp/run.log 2>&1", timeout=240)` then a separate `terminal(command="tail -30 /tmp/run.log")` to read back. **Do not trust `exit_code=0` alone** when running async-playwright through the agent's shell wrapper — verify by reading the log file.
- **browserclaw cookies decrypt output is wrapped, not a bare array (caught 2026-08-21).** `browserclaw cookies decrypt --output foo.json` writes `{"cookies": [...], "domains": [...]}`. The Playwright `BrowserContext.add_cookies()` API expects a bare array — passing the dict raises `BrowserContext.add_cookies: cookies: expected array, got object`. When bypassing `browserclaw cookies inject` and going straight to direct playwright (e.g. to control the dispatch loop), unwrap first: `cookies = raw['cookies'] if isinstance(raw, dict) and 'cookies' in raw else raw`, then also normalize: drop any keys outside `(name, value, domain, path, secure, httpOnly, sameSite, expires)`, and convert float `expires` → int (playwright wants integer epoch). **Recipe is in `references/transport-ladder-failure-log-2026-08-21-quiet-war.md`.**
