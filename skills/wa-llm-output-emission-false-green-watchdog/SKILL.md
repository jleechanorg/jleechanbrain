# wa-llm-output-emission-false-green-watchdog

The recurring false-green class at issue #9021 (re-confirmed by #9057): **tests pass because they encode the empty/default state as the expected outcome, masking an LLM-side regression that the production code path silently backfills around.**

The user's intuition "update the warning to look for code execution record" is the **WRONG fix** — masking the warning hides the real regression. The right fix is upstream: the served prompt must anchor the field with a worked example so the LLM can pattern-match against it on high-token turns.

## When to fire

Trigger on any of:
- User issues `/harness postmortem` on a WA bug with symptom pattern: `dice_rolls: []` / `action_resolution` absent / `planning_block` absent / `outcome_resolution` absent / `directives` missing / `state_updates` missing key sub-fields
- Hermes is reviewing a WA PR that touches `mvp_site/prompts/**` / `mvp_site/agent_prompts.py` / `mvp_site/narrative_response_schema.py` / `mvp_site/structured_fields_utils.py` / `mvp_site/llm_parser.py`
- A `/es` evidence check on a prompt-side fix needs served-prompt proof
- The `wa-daily-dice-audit` GCP cron exits 0 but the user is still reporting "missing X" in the UI
- A "merger safety" PR (refactor / cleanup) touches lines that contain a schema-anchor section that was added by an earlier fix
- The user reports "we merged a PR that should have fixed this" — verify the commit is on `origin/main`, not just on a feature branch
- **`wa-daily-dice-audit` cron exits 1 with `[Integrity Failure] has unparseable dice notation`** — audit-event-source field is corrupted by LLM-side prose (e.g. `FP_CALC...`, `4x 1d20+7`). This is the audit-event-source-side cousin of the LLM-output-side drift pattern. Same family as #9021 / #9057 / **issue #9021-sibling, 2026-08-18 GCP cron `wa-daily-dice-audit-2026-08-18` failure**.
- **User reports "X was always working before / X never had this issue before we changed Y"** on a WA prompt or model-config change. This is a regression signal — skip the static-evidence greps and go straight to `git log`/`git diff` for the suspect restructuring commit, then verify with the BQ wire-shape fingerprint (response_text=0 + parts>0 + finishReason=""). Verified 2026-08-18 on PR #9045 (`9c6f5d723b`, "refactor: decouple redundant model-computed arithmetic and centralize dice code execution prompts"). New Layer 5 recipe: `references/wire-shape-empty-finish-reason-2026-08-18.md`.
- **User reports literal `[object Object]` (or `[object HTMLDivElement]`, `[object Object]`, etc.) rendering in the JS-side dice-rolls / planning-block / choice panel**. This is a JS toString fallback on a dict-typed value, not an LLM regression. The cause is a partial-fix PR that added string coercion to ONE render path of a backfilled-dict-shaped field but missed a sibling render path. Verified 2026-08-19 on issue #9133 / campaign FsiyESY987DF2lfgolCI / PR #9054 + PR #9132 combination. Before grepping code, run `git log --oneline origin/main -- app.js | head -10` and search for sibling loops with `forEach` near the partial-fix lines. New Layer 8 recipe: `references/case-issue-9133-dice-rolls-object-object-render-path-2026-08-19.md`.
- **User reports "the world feels empty / factions don't move / background events don't fire"** OR **"the LLM invents enemies/troops/units instead of following the rules"** — narrative-invention-of-non-dice-side cousin. Symptom: LLM is fabricating unit counts, enemy rosters, troop strengths, faction moves that should be sourced from `faction_simulator` output but aren't because either (a) the simulation engine isn't wired into the deployed URL, (b) the canonical-state field is stripped before reaching the LLM, or (c) the prompt has no "source from canonical roster" anchor. This is a **structural-design gap** — NOT a per-turn regression of a single dice/planning field. Load `references/structural-design-gap-2026-08-19.md` (the 3-layer A/B/C diagnostic recipe) FIRST. Verified 2026-08-19 on campaign `ArYA47Fvx8HTYC8jpleO`: worldai_claw's complete WorldScheduler + faction_simulator engine exists but the deployed URL serves the Python backend (`mvp_site/living_world.py`), and `living_world_contract.py` strips `world_events` on cooldown turns. Different bug class from dice/planning emission regressions — this is about whether the deterministic simulation layer runs AT ALL.

## The 3-layer false-green guard

### Layer 1 — LLM-output-side vs audit-event-source distinction
The `wa-daily-dice-audit` GCP cron (`wa-daily-dice-audit-fix` skill) operates on the **audit-event source** ONLY (`dice_audit_events[]`, `notation` field integrity). It does NOT check whether the LLM emitted `dice_rolls[]` or `action_resolution` in `response_text`.

The two surfaces can drift — and did, in #9021 and #9057. A passing cron is NOT evidence the LLM-side emission works.

**Concrete bug pattern (verified #9057, turn 142):**
- `dice_audit_events`: `[]` (zero rolls this turn — pure narrative)
- `dice_rolls`: `[]` (LLM correctly emits empty)
- `action_resolution`: **absent** (LLM regression — should always emit for player actions)
- `tool_requests`: `[]`
- `state_updates`: only `world_data.{location, world_time}` and `custom_campaign_state.{core_memories, next_companion_arc_turn}`

The user's UI sees the warning because `_requires_action_resolution` at `mvp_site/narrative_response_schema.py:3513` correctly detects the missing field. The fix is NOT to mask the warning — it's to make the LLM emit the field.

**Companion bug pattern (`mvp_site/tests/test_structured_fields_utils.py:516`):** asserts `dice_rolls = []` and `len(result[FIELD_DICE_ROLLS]) == 1` (backfilled). This test passes because backfill works, but the LLM-side regression is silently masked. The test should be paired with a `test_regression_dice_rolls_emitted_when_code_execution_used` that asserts the LLM's structured response populated `dice_rolls` directly. **Out of scope for prompt-fix PRs — separate bead.**

### Layer 2 — Served-prompt contract test

Before approving any PR that touches `mvp_site/prompts/**` or `mvp_site/agent_prompts.py`, verify the served prompt contains a worked example for every Required structured-output field the LLM is expected to emit.

Concretely: `narrative_response_schema` declarations for `dice_rolls[]`, `action_resolution`, `planning_block` must each appear in the served prompt with at least one worked example (a JSON shape the LLM can pattern-match against).

Verified recipe (full contract test code in companion skill `wa-narrative-schema-required-fields-contract`):
- Pull real `request_json` from BQ (project `worldarchitecture-ai`, table `worldarchitecture-ai.llm_forensics.llm_payloads`)
- Grep for `"<field>":\s*[\[\{]` regex (worked JSON example)
- 0 occurrences for any Required field = regression signature

### Layer 3 — Audit/canary on LLM-output-side field, not audit-event source

When designing canaries for any LLM-side emission bug, ALWAYS add a canary on the LLM-output-side field (the field the LLM emits in `response_text`), separate from any canary on the audit-event source. The two can drift — and did, in #9021.

Canary surface: BigQuery `worldarchitecture-ai.llm_forensics.llm_payloads` filtered by `campaign_id` and `dice_rolls == [] AND dice_audit_events != []`. Expected invariant: `len(dice_rolls) > 0` whenever `len(dice_audit_events) > 0`. Violations are the regression signature.

## Recipe — 6 steps for any "missing X field" UI warning

### Step 0 — Sweep Firestore for the warning text first (don't hypothesize the cause)

Before assuming which mechanism produced the warning ("dice moved to code-execution, validator didn't follow" / "the PR refactor dropped a section" / "cache churn"), sweep the actual data. The `_server_system_warnings` array on each story entry is the authoritative surface — the warning is appended there when it fires and stays there indefinitely. The live UI is just re-reading these on every fetch.

The user's intuition about the cause may be reasonable-but-wrong. Verified 2026-08-19: user hypothesized "dice rolls moved to code-execution, validator didn't follow," but the actual cause was stale entries from May 2026 (pre-#9058). Recent dev-GCP turns had `action_resolution` populated correctly 117/117, even on the 80 turns where code-execution was the dice source. Hypothesis-fit is a SIGNAL, not proof.

Sweep query — see `references/case-action-resolution-stale-pre-9058-2026-08-19.md` for the full script + sample output. The core loop walks every campaign in `users/{uid}/campaigns`, fetches the last 100 story entries, filters `actor == 'user'` out (LLM-only), and tabulates `null_ar` (LLM omitted field), `warn` (validator fired the warning), `code_exec` (code-execution was the dice source), and `last_ts`.

Interpretation matrix:
- `warn > 0` AND `last_ts` is months old → warning is from a stale pre-fix era; live behavior is fine; tell user to hard-refresh the browser tab on that campaign.
- `warn > 0` AND `last_ts` is recent → real regression; proceed to Step 1 (BQ drill-down).
- `warn == 0` AND `null_ar > 0` → LLM is omitting `action_resolution` but validator is exempt (god-mode, character-creation, narrative-only, `_requires_action_resolution=False` context). Check the flag; usually not a bug.
- `warn == 0` AND `null_ar == 0` everywhere recent → live system is healthy; the warning user is seeing is from stale browser cache, an old campaign tab, a different surface (LLM parser test, `mvp_site/tests`), or an unrelated UI element.

Verified sweep result 2026-08-19 against jleechan's 1183 campaigns: 117 recent LLM turns across 5 active campaigns = `ar_present=117, warn_fired=0, code_exec_used=80`. All 11 warning-firing entries were from May 2026 (pre-#9058) in older campaigns, all `code_execution_used=False`, all `gemini-3-flash-preview`.

### Step 1 — Confirm the LLM genuinely didn't emit X (not a backend bug)

```bash
cd / && unset PYTHONPATH && bq query --use_legacy_sql=false --project_id=worldarchitecture-ai --format=csv "
SELECT response_text
FROM \`worldarchitecture-ai.llm_forensics.llm_payloads\`
WHERE campaign_id = '<CID>' AND turn_index = <TURN> AND agent = '<AGENT>'
LIMIT 1
" > /tmp/turn_X.csv
```

Then parse with Python and check the field at top-level of the LLM's JSON response. If field is absent or empty, the LLM regression is real — do NOT mask the warning.

### Step 2 — Get the served prompt (the 1.2MB row, not the 277-byte stub)

**NEW pitfall discovered 2026-08-18, issue #9057:** the BQ `llm_payloads` table contains **two rows per turn** — one with `turn_index=142` (the canonical row, where `request_json` is truncated to 277 bytes — a placeholder) and one with `turn_index=NULL` (the streaming-path row where `request_json` is the real 1.2MB payload). Both have `ingested_at` within 1 second of each other.

Query pattern that returns BOTH rows:

```sql
SELECT FORMAT_TIMESTAMP('%Y-%m-%dT%H:%M:%SZ', ingested_at) AS ts,
       turn_index,
       LENGTH(request_json) AS rj_len,
       LENGTH(response_text) AS rt_len
FROM `worldarchitecture-ai.llm_forensics.llm_payloads`
WHERE campaign_id = '<CID>'
  AND turn_index = <TURN>
ORDER BY ingested_at
```

You'll see two rows:
- `turn_index=<TURN>`, `rj_len=277` (placeholder)
- `turn_index=NULL`, `rj_len=1214259` (real served prompt)

To get the real one:

```sql
SELECT request_json
FROM `worldarchitecture-ai.llm_forensics.llm_payloads`
WHERE campaign_id = '<CID>'
  AND turn_index IS NULL
  AND FORMAT_TIMESTAMP('%Y-%m-%dT%H:%M:%SZ', ingested_at) = '<TS_OF_PLACEHOLDER -1s>'
  AND LENGTH(request_json) > 100000
LIMIT 1
```

CSV field size needs `csv.field_size_limit(sys.maxsize)` on Python 3.

### Step 3 — Grep the served prompt for the 3 things

```python
import re
served = open('/tmp/turn_X_served.csv').read()
for field in ['dice_rolls', 'action_resolution', 'planning_block']:
    text_count = len(re.findall(rf'\b{field}\b', served, re.IGNORECASE))
    worked = len(re.findall(r'"' + re.escape(field) + r'"\s*:\s*[\[\{]', served))
    print(f'{field:20s}: mentions={text_count}, worked={worked}')
```

**The smoking-gun pattern (verified #9057):**
- 73 mentions of `action_resolution` (all in past-turn history or schema prose)
- 0 worked JSON examples
- The "REQUIRED RESPONSE SCHEMA" anchor header from the fix is missing

### Step 4 — Verify the fix is on `origin/main`, not just on a feature branch

**NEW pitfall discovered 2026-08-18, issue #9057:** the user thought commit `098ca8316d` "fix(prompt): add REQUIRED response schema section for issue #9021" was merged. It was NOT. It lived on branch `fix/narrative-response-schema-required-9021` and never reached `origin/main`. Meanwhile, PR #9045 landed on `origin/main` today, making the situation worse by removing the only fallback prose that pointed the LLM at `action_resolution.mechanics.rolls`.

Verify before assuming any "merged" fix is actually deployed:

```bash
git -C ${HOME}/projects/worldarchitect.ai merge-base --is-ancestor <FIX_COMMIT> origin/main
echo "exit code: $?"  # 0 = on main, 1 = NOT on main
```

Then verify the deployed revision:

```bash
gcloud run revisions list --service=mvp-site-app-dev --region=us-central1 \
  --project=worldarchitecture-ai --limit 1 \
  --format="table(metadata.name,metadata.labels.commit-sha,status.conditions[0].status)"
```

The deployed revision's `commit-sha` must match the fix commit. If it doesn't, the fix isn't deployed.

### Step 5 — Trace the regression through the commit graph

When the served prompt is missing a section that a previous commit added:

```bash
# Find when the section disappeared
git -C ${HOME}/projects/worldarchitect.ai log --oneline -p -S "<SECTION_HEADER>" -- <PROMPT_FILE>
```

This will show every commit that added OR removed the section header. If you see only one commit (the addition), the section was never removed — meaning it was never merged to the branch you're looking at.

Then check branch containment:

```bash
git -C ${HOME}/projects/worldarchitect.ai branch --all --contains <FIX_COMMIT>
git -C ${HOME}/projects/worldarchitect.ai merge-base --is-ancestor <FIX_COMMIT> origin/main
```

If `branch --contains` shows only feature branches, the fix never reached main.

## NEW Layer 7 recipe (1.10.0, 2026-08-20)

### Validate-when-truly-missing pre-check pattern

When a validator fires a `Missing X field` warning that turns out to be **recovery-masked** — i.e. downstream code deterministically populates X from a sibling state field after the validator runs — do NOT only prune the warning at the recovery site. Move the check INTO the validator itself: only fire the warning when X is *genuinely* absent, by checking the sibling state FIRST.

```python
# BEFORE — post-hoc (PR #9132 v1): generate warning, prune later
if action_resolution is None:
    if not is_exempt:
        # ... append warning to _server_system_warnings ...
        # downstream add_action_resolution_to_response eventually strips it
        # from _server_system_warnings if dice_audit_events recovers ar
    return {}

# AFTER — pre-hoc (PR #9132 layer-top commit 28177a9953): check sibling state first
if action_resolution is None:
    dice_audit = getattr(self, "dice_audit_events", None) or []
    code_exec_used = bool(self.debug_info.get("code_execution_used"))
    truly_missing = not dice_audit and not code_exec_used
    if not is_exempt and truly_missing:
        # ... append warning to _server_system_warnings only now ...
    return {}
```

Three reasons the pre-hoc pattern is correct over post-hoc prune:
1. **No false-positive warning is ever generated** for the recovery path. The warning simply doesn't exist on `_server_system_warnings`, doesn't reach `system_warnings` via the `_merge_server_system_warnings_for_streaming_persistence` copy in `world_logic.py:9340-9362`, doesn't make the always-visible UI banner at `frontend_v1/app.js:1720-1741`. The user's question "Does it only show when debug mode enabled? It seems like it might always show it" — answered by pre-hoc fix.
2. **The narrative validator stays the single source of truth** for "truly missing" — recovery-masking logic isn't sprinkled across two prune sites that need to be kept in sync.
3. **The post-hoc prune code becomes belt-and-suspenders** for any case where the validator cannot see the sibling state at validation time (e.g. `code_execution_used` is set post-validator by `_enrich_streaming_structured_fields` in the streaming path). Keep the prune code; update its docstring to explain dual-path coverage.

Apply this pattern to any future validator field where downstream code could plausibly fill the field after validation: validator runs once → warning persists → recovery fills it → no one clears the warning. Equivalent: warning logic should be a property of the full picture at all reachable call sites, not just at validation time.

- **Don't trust the user's cause hypothesis — sweep Firestore first.** When a user reports a recurring warning + offers a cause ("dice moved to code-execution, validator didn't follow" / "PR refactor dropped a section"), the cause may be plausible-but-wrong. The cost of sweeping all of their campaigns + last 100 LLM entries via `db.collection(...).story` is ~3 minutes for a 1000+ campaign user; the cost of chasing the wrong fix is hours. Verified 2026-08-19: user's hypothesis was that the validator didn't follow the dice-into-code-execution move; sweep showed the validator worked correctly on 80 code-execution turns and the only warning-firing entries were from May 2026 (pre-#9058). See `references/case-action-resolution-stale-pre-9058-2026-08-19.md` for the sweep script + interpretation matrix. The hypothesis-fit is a SIGNAL to investigate, never proof.
- **The warning text isn't in the saved entry text — it's in `_server_system_warnings`.** When you grep the saved `.txt` archives for the literal warning string ("Missing action_resolution field"), you'll find ZERO hits even when the warning is firing. The validator at `mvp_site/narrative_response_schema.py:3447` appends the warning to `self.debug_info["_server_system_warnings"]`, which gets persisted on the story entry doc — NOT in the entry's `text` field that `document_generator.get_story_text_from_context_enhanced` renders. The right surface is `e["debug_info"]["_server_system_warnings"]` on each Firestore story doc, not the entry text. The same pattern likely applies to other UI warnings that originate in `NarrativeResponse._validate_*` methods.
- **JS-side refactors can silently drop a CSS hook attribute (NEW Layer 6, PR #9104, 2026-08-19).** The misleading Bugbot summary shape is `"risk styling on the <BUTTON/ELEMENT> via <CLASS> is unchanged"` — it describes ONE CSS hook site (button-level class) but does NOT verify the OTHER CSS hook site (row-level `[data-X]` attribute). When a JS-side refactor drops an attribute from an HTML element, ANY CSS rule using `[data-X]` / `[data-X="..."]` attribute selectors to style that element will silently break — even though the Bot Review says "unchanged." Verified recipe: when the bot summary or your own diff review identifies an attribute being dropped, grep the production CSS files (`mvp_site/frontend_v1/styles/**/*.css` and any other `*.css` files referenced in `index.html` or the entrypoint) for `[data-X]` / `[data-X="..."]` selectors that depend on it. If any CSS rule styles the dropped attribute, the refactor is broken regardless of what the summary says. Specifically for PR #9104: `parsePlanningBlocksJson` at `mvp_site/frontend_v1/app.js:3042 + 3068` dropped `data-risk="${riskLevel}"` from both `.choice-row` divs; `planning-blocks.css:112+` styles `.choice-row[data-risk="safe"]`, `.choice-row[data-risk="low"]`, `.choice-row[data-risk="medium"]`, `.choice-row[data-risk="high"]` for row-level Direction 4 risk tinting; the contract test `planning_block_risk_tint.test.js` test 4 catches it (`not ok 132 - parsePlanningBlocksJson emits data-risk on every .choice-row`). The fix: restore the attribute on both render paths — verified at commit `c7000ef359` for `jleechanorg/worldarchitect.ai#9104`, 300/300 frontend tests pass locally + core-mvp-1 self-hosted CI passes. General recipe: when reviewing a WA PR that drops an attribute (or refactors a render path that previously emitted it), grep the CSS for that attribute selector BEFORE trusting any "X is unchanged" bot summary. New reference: `references/case-pr-9104-css-hook-data-risk-drop.md`.
- **Verify the validator exemption matrix per agent (NEW Layer 7, PR #9132, 2026-08-19).** The validator at `mvp_site/narrative_response_schema.py:3413` respects `_requires_action_resolution` per-agent. Agents loading lightweight prompt sets (NARRATIVE_LITE / faction_management) do NOT have a schema anchor for `action_resolution` in their served prompt, so the LLM legitimately omits the field — but if the agent doesn't override `requires_action_resolution = False`, the validator fires "Missing action_resolution field" on every turn. Verified distribution on `29l48q6zFo7chxWnyjEY`: DialogAgent 7/9, HeavyDialogAgent 3/5, StoryModeAgent 3/4, FactionManagementAgent 1/1 (all missing or partially missing exemption); GodModeAgent 0/11, PlanningAgent 0/8, CharacterCreationAgent 0/3, LevelUpAgent 0/1, SpicyModeAgent 0/1 (all correctly exempt). Exemption inheritance caveat: HeavyDialogAgent + SpicyModeAgent extend DialogAgent, so adding the override to DialogAgent covers all three. When auditing or adding a new agent, ALWAYS check (a) whether it loads a lightweight prompt set without `action_resolution` schema anchor AND (b) whether its `requires_action_resolution` property returns False. The exemption is one line per agent class — keep the matrix complete, don't let new agents inherit the base default without explicit thought. Recipe: `grep -B1 -A4 "requires_action_resolution" mvp_site/agents.py` shows the full matrix. If a new agent shows up and the grep doesn't list it, that's a coverage gap.
- **Validator-then-recovery race leaves stale warnings (NEW Layer 7, PR #9132, 2026-08-19).** When the validator runs first and downstream code later populates the field, the warning persists in `debug_info._server_system_warnings` forever (it stays on the Firestore story entry doc and surfaces on every UI reload). Verified on `29l48q6zFo7chxWnyjEY`: every warning-firing entry had `action_resolution` populated AND `code_execution_used=True` AND `dice_audit_events` non-empty — the recovery happened post-validation via `add_action_resolution_to_response` at `world_logic.py:10368` reading from audit events. The fix: after `add_action_resolution_to_response` populates `action_resolution`, prune any "Missing action_resolution field" warning from `unified_response.debug_info._server_system_warnings`. Do this in BOTH the streaming path (`_merge_server_system_warnings_for_streaming_persistence` in `llm_parser.py:639`) AND the non-streaming path (`add_action_resolution_to_response` itself in `action_resolution_utils.py:962`). Apply this pattern to any future validator field where downstream code could plausibly fill the field after validation: validator runs once → warning persists → recovery happens → no one clears the warning. New reference: `references/case-pr-9132-agent-exempt-validator-recovery-2026-08-19.md`.
- **Trust user-provided evidence over your own aggregate sweep (NEW workflow pitfall, 2026-08-19).** When the user supplies a specific evidence surface — a campaign URL, a screenshot, a recent-turn TS, a Slack thread quote — and your own aggregate sweep says "no problem," the sweep is wrong, not the user. Verified 2026-08-19: my first sweep across jleechan's most-active 5 campaigns (chosen for being the largest + most recent) returned `ar_present=117, warn_fired=0, code_exec_used=80` — suggesting the validator was healthy. The user then sent a screenshot from a DIFFERENT campaign (`29l48q6zFo7chxWnyjEY`) showing the warning live; re-running the same sweep on that specific campaign returned `warn_fired=14/43 (32.6%)`. The lesson: an aggregate sweep across a convenience subset is not the same as sweeping the campaign the user is actually seeing. If the user provided a URL / screenshot / campaign ID, sweep THAT, not your preferred subset. Aggregate sweeps are useful for "is this widespread or isolated?" but they cannot refute a specific user-reported symptom. Recipe: when user evidence conflicts with your sweep, trust the user; re-sweep on the user's specific surface; if the second sweep contradicts the first, the difference is the answer (different agent / different prompt set / different code-execution status / different campaign age).
- **A partial-fix PR only fixes the path it touches — sibling render paths ship the same symptom (NEW Layer 8 pitfall, 2026-08-19, issue #9133).** When a bug involves a JS-side render of a structured field whose shape can be either string OR dict (e.g. backfilled from `dice_audit_events` via `structured_fields_utils.py:79-114`), a partial-fix PR adds label extraction OR string coercion to ONE render path but does NOT audit sibling paths. The symptom then shifts to the unpatched path. Verified on PR #9054 (merged 2026-08-18): added `rollLabel` fallback to the `mechanics.rolls[]` extraction at `app.js:1605-1647` but missed the sibling `<li>${sanitizeHtml(roll)}</li>` at `app.js:1713` — same dict shape, different code path, same `[object Object]` result. Detection recipe when reviewing PRs that touch a render function: (1) `grep -nE '\.forEach\b|\.map\b' mvp_site/frontend_v1/app.js | grep -B1 -A1 <partial_fix_function>`; (2) `grep -nE 'sanitizeHtml\(roll\)|sanitizeHtml\(item\)|sanitizeHtml\(entry\)' mvp_site/frontend_v1/` for sibling loops that consume the same field without coercion; (3) if the partial-fix introduces a per-item label extraction OR shape-conversion in ONE branch, audit ALL sibling branches consuming that field. Recovery shape: in the unpatched path, coerce dict→string with `[roll.roll, '=', roll.result, roll.label ? ' (' + roll.label + ')' : ''].filter(Boolean).join('')` before sanitizeHtml. Add a contract test that asserts the rendered HTML for a dict input does NOT contain `[object`. Cross-cut with Layer 1: this is the FRONTEND cousin of the LLM-output-side vs audit-event-source drift — when the backend backfills data shape into a field the frontend used to receive as one type, every frontend consumer needs to handle the new shape, not just the one the partial-fix PR touched.
