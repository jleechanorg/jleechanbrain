# Share-Landing Render Encoding Bugs

Session-specific detail for the `\u2019` literal-render bug on
`/shared/<token>` (verified 2026-08-18, fix PR
[jleechanorg/worldarchitect.ai#9100](https://github.com/jleechanorg/worldarchitect.ai/pull/9100)).

This is the canonical write-up to consult when:

- A user reports `King\u2019s Landing` / `\u2014` / `\u00d7` literals
  rendering verbatim on `/shared/<token>` or `/api/shared/<token>`.
- A campaign with LLM-generated descriptions shows escape sequences
  that the LLM never produced.
- The `/api/shared/<token>` JSON returns a string with embedded `\uXXXX`
  literals that the frontend then displays literally.
- The same symptom appears on a different rendering endpoint — the
  decoder pattern is generic; copy `_decode_embedded_unicode_escapes`
  into the new module and apply it before any HTML/JSON serialization.

Note the `setting` field: `King\\u2019s` — the JSON string literally contains
**double-escaped** Unicode. `\\u2019` decoded once by `json.tool` becomes
`\u2019` (the six-character literal backslash-u-2-0-1-9), and **that** is
what Firestore returned. The 4-char `\u2014` in `description` decoded
properly (it's correctly-encoded), so the bug is selective — only the
`setting` field went through a second round-trip.

## Why this happens — three plausible causes

1. **LLM output JSON-encoded twice.** The setting string was generated by
   the LLM as `"...King\u2019s Landing..."`, the LLM service JSON-serialized
   it once (producing `"...King\\u2019s Landing..."` in the JSON wire
   payload), the server-side writer then JSON-serialized the wire
   payload again before persisting — so the wire payload's
   `\\u2019` (a JSON escape) was stored as the literal 6-char sequence
   `\u2019` instead of being decoded to U+2019 first.
2. **Direct Firestore write with pre-escaped string.** A script wrote the
   string with `\\u2019` already in it, bypassing the normal
   write-decoding path.
3. **Test fixture / seed data.** A test created the campaign with a
   `setting` containing literal `\u2019` characters and the bug shipped
   to prod before someone noticed.

The fix doesn't need to know which one — it decodes the literal at read
time so any of the three upstream causes produces the right output.

## Why `markupsafe.escape` is the wrong layer for the fix

`markupsafe.escape` (used inside `render_shared_landing_page` to produce
the HTML-escaped `<h1>{title}</h1>` block) encodes the **5 standard
HTML-special characters**: `& < > " '`. It does **not** decode
`\uXXXX` / `\xNN` / `\UXXXXXXXX` sequences. So a 6-char literal
`\u2019` flows through `markupsafe.escape` untouched and ships to the
browser verbatim.

Same story for `json.dumps` — it doesn't decode embedded escapes, it
encodes them again (which would produce `\u005Cu2019` if you naively
re-serialized).

The fix has to **decode first, escape second.**

## The fix — `_decode_embedded_unicode_escapes()`

Applied to `mvp_site/share_token.py`, called from both
`get_shared_payload()` (JSON endpoint) and `render_shared_landing_page()`
(HTML page) on `title`, `setting`, `description` BEFORE the existing
`markupsafe.escape()` call.

```python
import re

_EMBEDDED_UNICODE_ESCAPE_RE = re.compile(
    r"\\u[0-9A-Fa-f]{4}|\\x[0-9A-Fa-f]{2}|\\U[0-9A-Fa-f]{8}"
)

def _decode_embedded_unicode_escapes(value):
    if not isinstance(value, str) or not value:
        return value
    if not _EMBEDDED_UNICODE_ESCAPE_RE.search(value):
        return value  # byte-identical pass-through
    out, i, n = [], 0, len(value)
    while i < n:
        ch = value[i]
        if ch != "\\" or i + 1 >= n:
            out.append(ch); i += 1; continue
        nxt = value[i + 1]
        if nxt == "u" and i + 5 < n and all(c in "0123456789abcdefABCDEF" for c in value[i + 2 : i + 6]):
            out.append(chr(int(value[i + 2 : i + 6], 16))); i += 6
        elif nxt == "U" and i + 9 < n and all(c in "0123456789abcdefABCDEF" for c in value[i + 2 : i + 10]):
            out.append(chr(int(value[i + 2 : i + 10], 16))); i += 10
        elif nxt == "x" and i + 3 < n and all(c in "0123456789abcdefABCDEF" for c in value[i + 2 : i + 4]):
            byte_val = int(value[i + 2 : i + 4], 16)
            out.append(bytes([byte_val]).decode("latin-1")); i += 4
        else:
            out.append(ch); i += 1  # unknown escape — keep the backslash
    return "".join(out)
```

### Why a custom walker and not `codecs.decode(..., "unicode_escape")`

`codecs.decode(b"...\\xF0\\x9F\\x98\\x83...", "unicode_escape")` returns
the 4-char string `'ð\x9f\x98\x83'` — the codec interprets `\xNN` as a
single ISO-8859-1 byte, which **silently breaks UTF-8 multi-byte
sequences**. The custom walker treats `\u` / `\U` as Unicode code points
(single Unicode character each, regardless of UTF-8 byte width) and
`\x` as a single UTF-8 byte fragment — the right semantics for the bug.

### Why the regex pre-check

Without it, every string would round-trip through the decoder. For a
string that already contains real Unicode characters (e.g. a user
pasted an em dash), the decoder would either pass it through
unchanged (best case) or silently transform valid content (worst case,
if any `\\` in the string got misread). The regex pre-check is the
**gating invariant**: the decoder runs **only** when an embedded
escape pattern is present.

## Where else this fix pattern applies

Any module that takes a string from Firestore (or any other JSON-backed
storage) and either:

- Inlines it into HTML (apply before `markupsafe.escape` or
  equivalent)
- Inlines it into a JSON response (apply before `json.dumps`)
- Inlines it into a CSV / YAML / shell context (apply before any
  string interpolation)
- Inlines it into a log line (apply before logging — a literal
  `\u2019` in a log is just as confusing as in a UI)

…is a candidate. If you find one, copy the helper into that module and
apply it before the existing serializer. Do **not** try to fix the
write path (Firestore / API request handler) — the upstream cause is
rare and the read-time decoder handles all three plausible causes
identically.

## Related bugs to watch for

- **HTML entities (`&amp;`, `&lt;`, `&gt;`) in user-supplied text** —
  same class of bug. The decoder pattern generalizes: a regex-gated
  pre-pass that decodes any structured escape literal before
  HTML-escape.
- **JSON wire-format double-encoding (`\"` in a string field)** — same
  class, different escape. If you see `\"` in a Firestore-stored
  string, that's a JSON double-encode bug; the fix pattern is the
  same (regex-gated pre-pass) but the regex and decoder target
  different characters.
- **Shell metacharacter leakage (`$`, `` ` ``, `\\`)** — if a Firestore
  string flows into a shell command, those chars get evaluated. The
  fix is `shlex.quote()` at the boundary, not at read-time.

If you hit one of these, lift the pattern from this reference and
adapt — don't reinvent.
