## Pitfalls (new patterns to add to `pr-ready-checklist`)

### P1 — `conclusion == ""` is NOT a failure

The original Gate 3 filter `select(.conclusion == "FAILURE" or .conclusion == "CANCELLED")` in `pr_ready_checklist.sh` returned FAIL whenever ANY check was in-flight (queued/pending/in_progress), because in-flight rows have `conclusion == ""` or `conclusion == null`. The audit spent the first ~30s wrongly believing 10+ checks had failed when they were simply still running.

**Fix**: use the FAILURE-only filter, then separately audit CANCELLED rows to determine whether they're infrastructure flake (superseded by a new push) or a real failure.

```bash
# Real failure count:
gh pr view <N> --json statusCheckRollup --jq '[.statusCheckRollup[] | select(.conclusion == "FAILURE")] | length'
# vs. in-flight count (NOT failures):
gh pr view <N> --json statusCheckRollup --jq '[.statusCheckRollup[] | select((.conclusion == null or .conclusion == "") and .name != null)] | length'
```

`CANCELLED` jobs that result from a superseded commit (re-triggered by a new push) are infrastructure flake. Use `gh run view <id>` to see the cancel reason — if it's a `limit-pr-runs` job-control cancellation, NOT a code failure.

### P2 — Evidence Gate is N/A when the workflow doesn't run

`Evidence Bundle Validation` only triggers on paths matching `.github/workflows/evidence-gate.yml`'s `paths:` filter:

```yaml
on:
  pull_request:
    paths:
      - "testing_mcp/**"
      - "testing_ui/**"
      - "deploy.sh"
      - ".github/workflows/evidence-gate.yml"
```

A PR that only touches `mvp_site/**` (or other non-`testing_*` paths) will have **no Evidence Gate row in the rollup at all**. The original `pr-ready-checklist` Gate 8 check `select(.name == "Evidence Gate") | .conclusion` would return an empty string when no row exists, which the script then compared to `"SUCCESS"` and reported FAIL — a false positive.

**Fix**: confirm the workflow's `paths:` filter before deciding, OR change the gate semantics to "if a row exists, must be SUCCESS; if no row, N/A pass":

```bash
gh pr view <N> --json statusCheckRollup --jq \
  '[.statusCheckRollup[] | select(.name | test("[Ee]vidence"))] | length'
# 0 = N/A pass; >=1 = each row's .conclusion must be "SUCCESS"
```

### P3 — Same-name pre-existing reproduction (verified end-to-end on this PR)

When `test_world_time_progression.py::test_maybe_update_living_world_tracking_skips_invalid_return` failed at `mvp_site/world_logic.py:950` with `AttributeError: 'BadGameState' object has no attribute 'world_data'`, the obvious mistake is to "fix" `mvp_site/world_logic.py` or write a contract test. But the PR does NOT touch `world_logic.py:950` — the failure is in a code path the PR never modifies. The same-name reproduction recipe from `qa-test-failure-dismissal-anti-pattern` applies.

**Recipe (verified PR #9150):**

```bash
# 1. Find the merge base of the PR branch
git fetch origin main
MERGE_BASE=$(git merge-base origin/main HEAD)
# On PR #9150: MERGE_BASE = 528ddd5147ca081479ee3cefe1aaf224f26e91ef

# 2. Spin up a detached worktree at the merge base (no PR changes applied)
git worktree add /tmp/wa-baseline "$MERGE_BASE" --detach

# 3. Run the failing test on the merge base
cd /tmp/wa-baseline
${HOME}/projects/worldarchitect.ai/venv/bin/python -m pytest \
  mvp_site/tests/test_world_time_progression.py::test_maybe_update_living_world_tracking_skips_invalid_return \
  --tb=line -q
# Result: same AttributeError, same file:line. PRE-EXISTING, not a PR regression.

# 4. Clean up
cd - && git worktree remove /tmp/wa-baseline --force
```

When documenting this in the `/ready` reply, quote the **exact** error string from both runs side-by-side. Don't dismiss with vague "pre-existing on main" — name the SHA, the test name, the file:line, and the assertion text.

On PR #9150 this applied to 27 test failures across 3 files: `test_world_time_progression.py` (1), `test_always_json_mode.py` (2), `test_divine_prompts_setting_agnostic.py` (24). All reproduced identically on `origin/main @ 528ddd5147ca`.

### P4 — GraphQL `resolveReviewThread` for chatgpt-codex-connector threads

`chatgpt-codex-connector[bot]` review threads do **not auto-resolve** even after the codex bot acknowledges the fix. Gate 7 stays FAIL until you explicitly call the GraphQL `resolveReviewThread` mutation per thread. The fix-up sequence on PR #9150 was:

```bash
# 1. Find unresolved thread IDs
gh api graphql -f query='{ repository(owner: "jleechanorg", name: "worldarchitect.ai") { pullRequest(number: 9150) { reviewThreads(first: 50) { nodes { id isResolved comments(last: 1) { nodes { body path line } } } } } }' \
  --jq '.data.repository.pullRequest.reviewThreads.nodes[] | select(.isResolved == false) | {id, body: .comments.nodes[0].body[0:200], path: .comments.nodes[0].path, line: .comments.nodes[0].line}'

# 2. Post a comment on each thread with the fix + commit references (BEFORE resolving)
gh api repos/jleechanorg/worldarchitect.ai/issues/9150/comments \
  -f body="@chatgpt-codex-connector addressed in commit ea6daa46a2 — ..."
# (comment IDs from this audit: 5378648585 thread 1, 5378649864 thread 2)

# 3. Resolve each thread via GraphQL
gh api graphql -f query='mutation { resolveReviewThread(input: {threadId: "PRRT_kwDOO8L8Qs6atWvH"}) { thread { id isResolved } } }'
gh api graphql -f query='mutation { resolveReviewThread(input: {threadId: "PRRT_kwDOO8L8Qs6atWvN"}) { thread { id isResolved } } }'
```

**Critical ordering**: comment first, then resolve. The comment preserves the audit trail ("why was this resolved?"); resolving without commenting leaves a "ghost resolved" thread with no public explanation. The `drive-pr-to-green` skill mentions `resolve_review_threads.sh` in passing, but does NOT document the comment-then-resolve ordering.

## The prompt-contract-hash refresh (new Step 5 substep)

When the PR legitimately changes `mvp_site/prompts/**/*.md` or `mvp_site/narrative_response_schema.py`, the `Prompt / Tool Contract Hash Validation` CI check (part of `Presubmit Checks` workflow) detects drift between the file content and the recorded hash in `mvp_site/schemas/prompt_tool_contracts.json`. The fix is mechanical:

```bash
# 1. Verify the drift is real
./venv/bin/python scripts/validate_prompt_tool_contracts.py
# Output: "prompt/tool contract validation failed: ... Run --update to refresh"

# 2. Update the manifest
./venv/bin/python scripts/validate_prompt_tool_contracts.py --update
# Output: "Updated hash-derived version for mvp_site/prompts/game_state_instruction.md: c2dc968aa868 -> a77474f681c9"
#          "Updated hash-derived version for mvp_site/narrative_response_schema.py: a0dfd910c817 -> 3f3e3ca16572"

# 3. Verify clean
./venv/bin/python scripts/validate_prompt_tool_contracts.py
# Output: "prompt/tool contracts validated"

# 4. Commit
git add mvp_site/schemas/prompt_tool_contracts.json
git -c user.name=hermes -c user.email=hermes@MiniMax.local commit \
  -m "claudem/minimax-M3: chore(contracts): refresh prompt/tool hash manifest"
```

The hash-derived version IS the content hash, so no semver or counter-sync is needed.

**Trigger this whenever the PR diff includes any of:**
- `mvp_site/prompts/**/*.md`
- `mvp_site/narrative_response_schema.py`
- `mvp_site/schemas/*.json` (especially `prompt_tool_contracts.json` itself)
- `mvp_site/agent_prompts.py` (path manifest)

This is a "must run before push" step that is missing from `drive-pr-to-green` Step 5.

## Pre-existing worktree state mismatch

When the audit started, the local worktree at `${HOME}/projects/worldarchitect.ai/_wt/feat-planning-block-narrative-only` was checked out at `550b28c270` (the original commit from 2 days prior), but the PR head on origin was already `30a8cf8f00` (a merge commit with 2 newer commits on top). Resetting the worktree to `origin/feat/planning-block-narrative-only` via `git reset --hard` was the right move; without it, the `git push` would have force-pushed the local older state over the newer origin state, losing the merge commit + the 2 follow-up commits. Lesson: **always verify worktree HEAD equals `gh pr view <N> --json headRefOid` before any force-push**.
