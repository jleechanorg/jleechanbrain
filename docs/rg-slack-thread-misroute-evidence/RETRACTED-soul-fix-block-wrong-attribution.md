## COMMIT: slack-send-tool-must-carry-thread-ts
Trigger: ANY `send_message` tool call targeting Slack while the current session is a thread session (i.e. `$HERMES_SESSION_THREAD_ID` is non-empty) — status narrations, progress updates, worker acks, "Corrected:", "/repro done", spot-checks, blockers, completion reports. Applies to every follow-up post in an in-flight flow, not to genuine first-contact announcements in a silent channel.
Action: Use the **thread target form** `slack:<channel_id>:<thread_ts>` — e.g. `slack:${SLACK_CHANNEL_ID}:1786619681.886529`. Do NOT use the bare `slack:<channel_id>` / `slack:#channel` form for a follow-up; that form posts at CHANNEL ROOT and is the misroute Jeffrey keeps reporting. Resolve `<thread_ts>` from `$HERMES_SESSION_THREAD_ID` (read it with the terminal tool: `echo "$HERMES_SESSION_THREAD_ID"`) or from the thread you are replying in. If you cannot resolve a thread_ts, do NOT post the update — log to stderr instead.
Why the tool schema misleads you: `send_message`'s own `target` description documents the `chat_id:thread_id` form as being "for Telegram topics and Discord threads" and shows only bare-channel Slack examples (`slack:#engineering`) — but `tools/send_message_tool.py:34,551-554` fully supports Slack thread targets. Trust THIS rule over the tool description. The tool also never reads `$HERMES_SESSION_THREAD_ID` (it reads `HERMES_CRON_AUTO_DELIVER_THREAD_ID` but not the session one), so nothing auto-threads your post for you — you must pass it explicitly.
Bug-ref: 2026-08-15/16 #all-jleechan-ai (${SLACK_CHANNEL_ID}) — four consecutive hermes posts (ts 1786848921, 1786857696, 1786858256, 1786859782) landed at channel root with empty thread_ts while Jeffrey's messages carried `thread_ts=1786619681.886529`. Root cause is this schema/session-var gap, NOT the previously-patched shell/python misroute paths (PRs #603/#606/#609/#617/#29).
